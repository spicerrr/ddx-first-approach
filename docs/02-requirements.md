# 02. Сценарии и требования

## Сценарий MVP

| Шаг | Вход | Действие и проверка | Выход |
| --- | --- | --- | --- |
| S1 «Гантели» | 6 гантелей: 8, 12, 16 кг, по две каждой | собрать 3 пары и положить каждую в секцию соответствующего веса; сервер проверяет все ID и секции | S2 |
| S2 «Штанга» | гриф 20 кг; на каждой стороне уже по 20 и 5 кг; цель 77,5 кг; доступны пары блинов 1,25, 2,5, 5, 10 кг | положить по 2,5 и 1,25 кг на каждую сторону; сервер проверяет симметрию и массу: 20 + 2 × (20 + 5 + 2,5 + 1,25) = 77,5 | событие помощи |
| H «Посетитель» | персонаж просит показать регулировку скамьи; пример контента — Foreman FW-702 | на вращаемой модели по очереди найти фиксатор спинки, показать перемещение и фиксацию, затем рычаг сиденья, перемещение и фиксацию; сервер принимает 6 шагов по порядку | S3 |
| S3 «Инвентарь» | 8 объектов: по 2 коврика, МФР-ролла, фитбола и куба; вид зала сверху | распределить все 8 по четырём отмеченным зонам, проверка каждого ID | результат |
| R «Результат» | завершённая сессия | показать завершение, новый запуск и переход в существующий Smart Start | новая сессия или навигация |

Ошибочный ответ не сбрасывает станцию. Число попыток не ограничено; оно измеряет сложность задания. Содержимое сценария возвращается вместе с сессией и фиксируется её `scenarioVersion`: публикация новой версии не меняет начатые партии.

## Функциональные требования

| ID | Требование |
| --- | --- |
| REQ-01 | Приложение показывает вход в игру только при включённом флаге и подтверждённой сервером доступности; активная сессия открывается через «Продолжить». |
| REQ-02 | Запуск создаёт одну ACTIVE-сессию со снимком сценария; повторный запуск при незавершённой сессии возвращает конфликт и её ID. |
| REQ-03 | На каждом этапе сервер принимает полное расположение объектов по их ID и проверяет его на снимке сценария. Переход возможен только после правильного ответа. |
| REQ-04 | После верной штанги сессия переходит в PAUSED_HELP; шесть действий по регулировке модели выполняются последовательно. Сервер хранит очередной шаг; неверный контроль или порядок оставляют паузу. Ответ следующей станции запрещён до шестого шага. |
| REQ-05 | Сервер сохраняет статус, этап, версию и попытки после каждого принятого действия; повторный вход с другого устройства восстанавливает тот же снимок. |
| REQ-06 | Завершение третьей станции переводит сессию в COMPLETED. После завершения, отказа или истечения можно создать новую независимую сессию; историю нельзя переписать. |
| REQ-07 | Из результата приложение открывает существующий Smart Start с меткой источника. Создание бронирования и проверка мест относятся к текущему модулю записи. |
| REQ-08 | Каждая команда изменения имеет ключ идемпотентности и ожидаемую версию; один ключ с тем же телом даёт тот же результат, а устаревшая версия не меняет состояние. |
| REQ-09 | Доступ к каждой сессии ограничен владельцем из авторизационного контекста, без ID пользователя в теле запроса. |
| REQ-10 | Сервер создаёт одну запись события на доменный факт; доставка сообщения может повторяться, получатель устраняет повторы по `eventId`. Клиентские открытия и клики учитываются отдельно, без данных посетителей. |
| REQ-11 | Клиент показывает понятный способ восстановления при потере сети: повторить ту же команду с тем же ключом, затем запросить текущее состояние. |
| REQ-12 | Сессия без активности истекает через 7 суток; истёкшую сессию нельзя изменить, но можно начать новую. |
| REQ-13 | Мобильный клиент хранит локальный черновик текущего этапа для той же учётной записи; без сети проверка не отправляется, а после восстановления состояние сверяется с сервером. Команда с неизвестным итогом повторяется с прежним ключом. |
| REQ-14 | Клиент объявляет поддерживаемую версию схемы задания. Несовместимый клиент получает 426 и не начинает сессию; начатая сессия сохраняет версию и снимок своего сценария. |
| REQ-15 | На iPhone при захвате блина воспроизводится один короткий тактильный импульс с градацией массы 1,25/2,5/5/10 кг; установка подтверждается отдельным мягким сигналом. Возможность отключения и текстовая/визуальная обратная связь обязательны. |
| REQ-16 | Переход из результата в Smart Start выполняется навигатором приложения с источником `shift_result`; вход по внешней ссылке в игру проверяет авторизацию и актуальное состояние серверной сессии. |
| REQ-17 | Серверные события публикуются по версионированному асинхронному контракту после фиксации команды, с ключом сессии, версией состояния и устранением повторов на стороне получателя. |
| REQ-18 | Модель оборудования из существующего раздела инструкций связывается с версионированным 3D-гайдом по `equipmentCatalogRef`; игра ссылается на тот же `guideId`, а без ассета доступно видео/текст. |
| REQ-19 | Клиент показывает отдельные клипы и подсказки для фиксатора/движения/блокировки спинки и сиденья, вращает модель и позволяет повторить клип. Просмотр сам по себе не подтверждает игровой шаг. |

## Нефункциональные требования для согласования

- **Согласованность:** команда, изменение состояния, попытка, ключ идемпотентности и запись исходящего события совершаются одной транзакцией.
- **Наблюдаемость:** requestId в ответе и логах, метрики 4xx/5xx, конфликтов версии, повторов и задержек; без содержимого токенов и личных данных.
- **Доступность клиента:** крупные активные зоны, текстовые подписи предметов/зон, управление без обязательного перетаскивания; альтернативный выбор «объект → зона».
- **Производительность:** целевой p95 ответа игровой API до 500 мс без учёта сети — гипотеза для пилота, уточняется по инфраструктуре DDX.
- **Совместимость:** клиент, не поддерживающий `scenarioSchemaVersion` или тип этапа, предлагает обновление приложения и не отправляет ответ.
- **Мобильная среда:** работа с плавающей сетью, локальным черновиком, устаревшими версиями клиента, тактильным откликом и внутренними маршрутами описана в [мобильных требованиях](10-mobile.md).
