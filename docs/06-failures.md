# 06. Ошибки, конкуренция и повторы

| Ситуация | Ответ | Поведение клиента |
| --- | --- | --- |
| неверная расстановка, масса или контроль/порядок в HELP | 200 `accepted:false`, `feedbackCode`, версия +1 | показать подсказку и текущее состояние; следующую попытку отправить с новым ключом/версией |
| неизвестный, отсутствующий или повторённый `itemId`; ответ другого типа; неверное число объектов | 400 INVALID_PAYLOAD, без новой попытки | восстановить интерфейс из GET, не повторять некорректное тело |
| истёк/нет токена | 401 UNAUTHORIZED | штатное восстановление входа в приложение, затем GET |
| выключен флаг или нет доступа при запуске | 403 FEATURE_UNAVAILABLE | объяснить недоступность; не создавать сессию |
| уже есть активная сессия при новом START | 409 ACTIVE_SESSION_EXISTS + `activeSessionId` | предложить продолжение по GET |
| другой этап, терминальная сессия | 409 INVALID_TRANSITION | GET и перерисовка актуального состояния |
| срок истёк перед командой | 409 SESSION_EXPIRED | предложить новый запуск, старая история сохраняется |
| второй запрос с устаревшей версией | 409 VERSION_CONFLICT + `currentVersion` | GET; не переигрывать выбор пользователя автоматически |
| тот же `Idempotency-Key` с другим методом/путём/телом | 409 IDEMPOTENCY_KEY_REUSED | создать новый ключ только для новой осознанной команды |
| чужой `sessionId` | 404 NOT_FOUND | не раскрывать владельца |
| таймаут/5xx/разрыв после отправки | результат неизвестен клиенту | повторить буквально тот же метод, путь, тело и ключ; после неоднозначного ответа GET |
| сеть пропала до отправки | запроса на сервере нет | сохранить локальный черновик; при восстановлении сначала GET и только после сверки предложить отправить новый запрос |
| клиент не поддерживает формат сценария | 426 CLIENT_UPGRADE_REQUIRED | предложить обновление приложения; не пытаться собрать ответ по неизвестной схеме |
| недоступен Smart Start | ошибка существующего модуля | завершённая сессия остаётся COMPLETED; пользователь может повторить переход позже |

### Окно и семантика идемпотентности

- Ключ — UUID на **одну команду**. Сервер сохраняет HTTP-статус и тело обработанной команды в одной транзакции с эффектом. Повтор с тем же телом возвращает сохранённый ответ, даже если сессия уже ушла в следующее состояние. Для ошибок до транзакции (например, 401) результат не кэшируется.
- Для START при двух разных ключах действует уникальность одной незавершённой сессии. Один создаёт 201, другой видит 409 ACTIVE_SESSION_EXISTS.
- Версия проверяется после поиска записи обработанной команды. При двух разных командах с одним `expectedVersion` только одна фиксируется; другая получает 409 VERSION_CONFLICT.
- Каждая новая обработанная попытка (включая неверный ответ) обновляет `lastActivityAt` и `expiresAt = lastActivityAt + 7 суток`. GET и повтор сохранённого запроса срок не продлевают.
- Обработчик истечения и пользовательская команда конкурируют за одну строку; сравнение срока делается под блокировкой. Исходящее событие истечения появляется один раз.
- Доставка исходящих событий как минимум один раз. Потребитель устраняет повторы по `eventId`; пользовательский ответ не ждёт аналитическую платформу.

### Примеры

Сессия `ACTIVE/BARBELL v2`: правильный ответ с ключом K → `PAUSED_HELP/HELP v3`. Сеть оборвалась до получения ответа. Повтор K с тем же телом возвращает прежний `v3`, не создаёт вторую попытку. Новый ключ с `expectedVersion:2` получает VERSION_CONFLICT.

Сессия `PAUSED_HELP/HELP v3` с индексом 0: `SEAT_LEVER/seat_lever` → `accepted:false`, `WRONG_ORDER`, индекс 0 и v4. `BACK_PIN/back_pull_pin` с новым ключом и `expectedVersion:4` → индекс 1 и v5. После шести принятых действий следующий этап — EQUIPMENT.

Мобильный клиент при потере сети различает два случая: команда ещё не ушла (хранится только черновик) и команда ушла с неизвестным результатом (сохраняется исходный запрос с ключом). Последовательность восстановления и смены пользователя описана в [мобильных требованиях](10-mobile.md).
