# 11. Асинхронная публикация игровых событий

Контракт: [AsyncAPI 3.0](../contracts/asyncapi.yaml). Он описывает **предлагаемую** границу между игровым API и аналитикой. Из открытых материалов нельзя установить, использует ли DDX именно Kafka, как называются реальные темы и кто владеет брокером. Перед внедрением транспорт согласуется с командой интеграций; схема событий остаётся применимой и при другом транспорте.

| Параметр | Правило для проектного варианта |
| --- | --- |
| Тема | `shift.session.events.v1`; отдельное имя для версии контракта |
| Отправитель | игровой API публикует из таблицы исходящих событий после фиксации команды |
| Ключ сообщения | `sessionId`; события одной сессии сохраняют порядок в одном разделе темы |
| Семантика доставки | не менее одного раза; получатель устраняет повторы по `eventId` |
| Порядок | `eventSequence` растёт на единицу для каждого события сессии; несколько событий одной команды имеют одну `stateVersion`, но разные номера |
| Ошибка отправки | запись остаётся в исходящих событиях и отправляется повторно; ответ игроку не отменяется |
| Ошибка обработки получателем | повтор с ограничением по времени/числу попыток, затем карантин проблемного сообщения и сигнал в мониторинг; конкретная политика зависит от платформы DDX |
| Эволюция | добавление необязательных полей допускается в рамках версии при согласовании; переименование/удаление или изменение смысла — новая версия сообщения/темы |
| Персональные данные | только технический `sessionId`; идентификатор аккаунта в сообщение не включён |

Номер разделов, коэффициент репликации, срок хранения, сервер брокера, схема авторизации и название группы получателей здесь **не назначены**: их нельзя вывести из игрового сценария. Они задаются владельцем платформы по нагрузке и политике хранения. Клиентские `game_opened` и `smart_start_clicked` могут уходить через существующий мобильный сборщик аналитики и не являются сообщениями этого доменного канала. Событие подтверждённой записи Smart Start приходит из владельца бронирования, если такой контракт существует; игровой API его не производит.

Отправитель сохраняет порядок `eventSequence` в рамках `sessionId` и не отправляет более позднее событие той же сессии до подтверждения предыдущего. Ключ `sessionId` помещает события в один раздел Kafka; один лишь ключ без последовательной отправки недостаточен. Получатель отбрасывает повторный `eventId` и сигнализирует о пропуске номера.

### Сквозная согласованность

Успешная штанга фиксирует `PAUSED_HELP/HELP v3`, попытку и записи `game_stage_attempted`, `game_stage_completed`, `game_help_shown` в одной транзакции. После сбоя публикации они остаются в исходящих событиях. Повтор HTTP-команды с тем же ключом возвращает прежний ответ и не создаёт новых событий. Аналитический получатель может повторно получить сообщение, но использует `eventId` для однократного учёта.

Содержимое и формат спецификации сверены с [AsyncAPI 3.0](https://www.asyncapi.com/docs/reference/specification/v3.0.0) и [Kafka bindings](https://www.asyncapi.com/docs/reference/bindings/kafka).
