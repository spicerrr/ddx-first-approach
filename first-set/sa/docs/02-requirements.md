## Canonical MVP mechanics

Сценарий задаётся версией `scenarioVersion`; каждый правильный **атомарный** action продвигает позицию станции, неправильный возвращает объяснение без продвижения.

| Stage | Интерактивная операция | Условие завершения | Ограничение интерпретации |
|---|---|---|---|
| `DUMBBELLS` | Поместить три **пары** виртуальных гантелей 8/12/16 кг в подписанные ячейки | Каждая пара в соответствующей ячейке | Не реальная сортировка оборудования |
| `BARBELL` | Разместить виртуальные диски на левой/правой стороне так, чтобы конфигурация была симметричной | В демо: 5+10 кг **с каждой стороны**; параметры задаются сценарием | Не рекомендация тренировочного веса; не обучает фиксации грифа |
| `BENCH` | Пройти **шесть логических проверок безопасного обращения** с незнакомой скамьёй | Подтверждены все шесть шагов сценария | Не заменяет инструкцию к модели и тренера |
| `INVENTORY` | Распределить восемь виртуальных предметов по четырём обозначенным зонам хранения | Все предметы распределены верно | Расположение зон в клубах нужно подтвердить |

Для `BENCH` шесть проверок: зона свободна → скамья разгружена → найдена маркировка/инструкция модели → при неуверенности обратиться к тренеру → не применять силу к неизвестному механизму → перед работой проверить фиксацию/устойчивость. Это **концептуальные правила**, не пошаговая техническая инструкция для конкретного оборудования.

## Session invariants

1. Не более одной `ACTIVE` сессии на участника (атомарная уникальность по его серверному идентификатору).
2. Владелец извлекается из доверенной авторизации; в запросах нет `memberId`.
3. `scenarioVersion` и последовательность действий закреплены при создании сессии.
4. Сессия хранит `stage`, `stageProgress` и монотонную `revision`. При правильном действии revision повышается ровно на один; неверный игровой ответ не продвигает позицию.
5. Одинаковый `Idempotency-Key` + тот же payload возвращает **тот же результат**, включая после уже выполненного перехода. Один ключ с другим payload отклоняется.
6. Новый ключ + устаревшая `expectedRevision` → `409 STALE_REVISION` с актуальной сессией.
7. Переход к `COMPLETED` выполняется только после последнего правильного действия станции `INVENTORY`; CTA не изменяет статус.
8. Терминальные `COMPLETED`, `ABANDONED`, `EXPIRED` не принимают новые игровые действия; новая сессия создаётся отдельно, если разрешена правилами показа.
9. Запросы к чужой сессии маскируются под `404`; действие не выдаёт данные владельца.
10. Текущий демо-клиент **не** реализует эти серверные гарантии: localStorage здесь только mock состояния.

## Negatives & unresolved integration policy

- При сетевом таймауте — повтор **с тем же ключом**, не повторное создание нового действия.
- При конфликте ревизии — GET текущей сессии, затем показ принятого состояния; не повторять действие автоматически с новой ревизией.
- При отключении экспериментального флага действующая сессия в предлагаемой политике доступна для чтения/завершения, но новые предложения скрываются. Подтверждение DDX обязательно.
- Отсутствие мест в Smart Start не изменяет `COMPLETED`.
- Условие истечения сессии, retention, real eligibility и SLA определяются после согласования с владельцами платформы.
