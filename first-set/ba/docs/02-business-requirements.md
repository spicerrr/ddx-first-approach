# 02 · Requirements model: business → stakeholder → solution

Не называем каждое поведение интерфейса «бизнес-требованием». Уровни ниже различаются по **объекту утверждения** и **способу проверки**; отдельные свойства могут классифицироваться одновременно по типу и уровню.

## Business goals / outcomes

| ID | Целевой результат | Измерение | Статус |
|---|---|---|---|
| BG-01 | Повысить использование уже существующей программы адаптации среди новых членов | Фактическое посещение Smart Start или ознакомительной тренировки за 14 дней с момента активации | Гипотеза, не подтверждена |
| BG-02 | Улучшить понимание базовых правил обращения с инвентарём | Задания на понимание до и после, отложенная проверка | Гипотеза |
| BG-03 | Не ухудшить клиентский опыт и операционную нагрузку клуба | Пропуски онбординга, жалобы, доступность слотов, неявки | Ограничение эксперимента |

BG-01 — **primary outcome** для продуктового эксперимента. BG-02 — отдельный образовательный outcome. Удержание/LTV не являются доказанными результатами MVP.

## Stakeholder needs

| ID | Стейкхолдер | Потребность |
|---|---|---|
| SN-01 | Новый участник | Быстро найти правила и программы помощи перед самостоятельной тренировкой |
| SN-02 | Участник с опытом | Не проходить принудительную игру, не терять доступ к приложению |
| SN-03 | Продуктовая команда | Отличить эффект игры от эффекта обычной карточки и измерить посещение, не только клики |
| SN-04 | Тренеры/операции клуба | Не получать неконтролируемый поток записей сверх доступных слотов |
| SN-05 | Юридический/контентный владелец | Не представлять симуляцию как обучение реальной технике или допуск |

## Solution requirements — functional

| ID | Требование | Привязка |
|---|---|---|
| FR-01 | Показывать добровольный вход только пользователю, допущенному к эксперименту | SN-01, SN-02, SN-03 |
| FR-02 | Дать возможность пропустить предложение без изменения членства или основных сценариев приложения | SN-02 |
| FR-03 | Реализовать **четыре интерактивные станции** с действиями над виртуальным инвентарём | SN-01, BG-02 |
| FR-04 | Для некорректного действия выводить конкретное объяснение без продвижения; разрешать повтор | SN-01, BG-02 |
| FR-05 | Сохранять принятую сервером игровую сессию и восстанавливать её после перезапуска | SN-01 |
| FR-06 | После завершения показать памятку и передать пользователя в существующую навигацию вводных услуг | SN-01, BG-01 |
| FR-07 | Не создавать бронирование силами игрового домена и не делать вывод о правах пользователя по факту завершения игры | SN-04, SN-05 |
| FR-08 | Разделять экспозицию, старт, этапы, CTA, успешную запись и фактическое посещение | SN-03 |
| FR-09 | Поддерживать контрольную группу и сравнение с простой информационной карточкой | SN-03 |
| FR-10 | Обрабатывать повтор запроса, одновременные действия с устройств и устаревшее состояние | SN-01 |

## Business rules

| ID | Правило |
|---|---|
| RL-01 | Отказ от игры не ограничивает использование клуба и приложения |
| RL-02 | Игровые результаты не предоставляют тренировочную квалификацию или допуск |
| RL-03 | Условия и право записи определяются действующей системой DDX, не игровой сессией |
| RL-04 | Переход по CTA ≠ бронирование ≠ посещение |
| RL-05 | Тариф не создаёт платного ограничения для рассматриваемого обучающего контента |
| RL-06 | Контент не содержит универсальных физических инструкций для неизвестной модели тренажёра |

## Nonfunctional & integration constraints

| ID | Ограничение / требование | Проверка |
|---|---|---|
| NFR-01 | Доступность интерфейса с клавиатуры и на мобильном экране; обратная связь не только цветом | UX-проверка |
| NFR-02 | При сетевом повторе одного действия не возникает второй переход | Идемпотентный тест |
| NFR-03 | Посторонний пользователь не читает чужую сессию | Проверка авторизации / изоляции |
| NFR-04 | Клиент не может присвоить прогресс, передав произвольный `memberId` | Контекст авторизации |
| IC-01 | Не изменяем существующие платежи, тарифы, InBody и расписание | System context |
| IC-02 | Реальный маршрут записи/аналитики неизвестен и требует согласования | Open questions |
| IC-03 | Модель игрового сервера — *предложение*, не утверждение об архитектуре DDX | Явные границы модели |

Конкретные пороги производительности, SLA, сроки хранения, технические стеки и реализация интеграции **не заданы** без внутреннего контекста. Не заменяем их произвольными числами.

## Состояния AS-IS / TO-BE

**AS-IS (проверить):** активация → текущие коммуникации и навигация приложения → первые посещения → обнаружение/запись на вводные услуги или отказ. Порядок и видимость элементов не подтверждены.

**TO-BE (гипотеза):** предложение (можно пропустить) → четыре станции с пояснениями → памятка → переход к штатному экрану записи → подтверждение бронирования/посещения **в существующих процессах DDX**.
