# 03 · Validation strategy and experiment

[Кейс](../../../README.md) / [Карта артефактов](../../../NAVIGATION.md) / [BA · Бизнес-анализ](../README.md) / **03 · Validation Plan**

**Decision question:** создаёт ли интерактивный формат дополнительную ценность сверх простого и заметного информирования об уже существующих услугах DDX?

## G0 — существует ли проблема?

До разработки:

1. Аудит **текущего** пути клиента: приложение, первый вход, условия и доступность Smart Start/ознакомительной тренировки, все точки контакта. Зафиксировать дату, версию iOS/Android, клуб/тариф.
2. Интервью с недавно активировавшими членство: осведомлённость, нахождение услуги, попытки записи, прерывания, отсутствие свободных мест, реальные причины неучастия.
3. При доступе к данным: отдельные факты `awareness → eligible → booking attempt → booking confirmed → attendance`; число свободных слотов по клубу и дате.
4. Если обнаружения уже достаточно и основные причины — расписание, нежелание или ёмкость, решение **не строить игру** в прежней постановке.

## G1 — действительно ли игра нужна?

Сначала отдельно проверить простой вариант B (карточка правил и CTA). Вариант C рассматривается только при наличии доказательств, что пассивный информационный формат недостаточен для выбранного результата. Эксперимент ниже — возможный дизайн, не обязательная инвестиция.

| Вариант | Условия |
|---|---|
| A — control | Существующий onboarding |
| B — information | Та же точка входа, компактная карточка, тот же CTA |
| C — interaction | Та же точка входа, четыре игровые станции, тот же CTA |

**Единица рандомизации:** `memberId` при первичном входе в эксперимент; назначение закреплено для всего периода исследования. Различия B/C кроме интерактивности должны быть минимальны, иначе невозможно изолировать эффект. Если в A отсутствует точка входа, это следует учитывать при интерпретации A↔B/C.

## Метрики

**Primary (intention-to-treat):** количество уникальных рандомизированных новых участников, фактически посетивших ≥1 Smart Start / ознакомительную тренировку за 14 дней после активации членства, / число **всех рандомизированных новых участников** соответствующей группы. Не делить только на завершивших игру: это селекционное искажение.

**Secondary:** понимание правил (в том числе отложенное), знание услуги, запуск/завершение игры, открытие экрана записи, подтверждённая запись.

**Guardrails:** доля отказов, ошибки приложения, неявки, отмены, дефицит свободных мест по клубам, жалобы, нагрузка тренеров. **Важное ограничение:** рост спроса при неизменной ёмкости расписания может не увеличить посещения.

**Атрибуция:** разделять показ → клик → открытие записи → подтверждение → факт занятия. Нужен согласованный способ связать рандомизацию и события записи/посещений без передачи лишних персональных данных в игровые события.

## Экспериментальная дисциплина

- Окно 14 дней — проектное допущение, а не норматив DDX; перед пилотом согласовать с операциями и историческим циклом записи.
- Зафиксировать заранее: eligibility, критерии исключения, MDE, уровень ошибки, мощность, продолжительность набора, учёт повторных покупок/возобновлений и метод сравнения.
- Размер выборки рассчитывать **после** получения baseline, не придумывать числа.
- Стратифицировать или проверять дисбалансы по клубу, наличию свободных слотов, платформе, опыту посещений.
- Не утверждать рост удержания или выручки на основе роста кликов/игровых завершений.
- Негативный результат — основание отказаться от дорогой игровой реализации.

## G2 — переход к пилоту

Пилот имеет смысл только если: проблема подтверждена; B недостаточен; C улучшает релевантный outcome при приемлемых guardrails; ресурсы тренеров и интеграционный маршрут позволяют исполнить обещание пользователя. Разработка масштабного контента или отдельного сервиса до этих условий не оправдана.

**Экономическая оценка:** прирост доказанного маржинального вклада и подтверждённой экономии − стоимость разработки/поддержки − нагрузка на вводные услуги. Любые численные значения потребуют данных DDX.
